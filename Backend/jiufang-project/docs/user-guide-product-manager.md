# 产品经理使用指南

本指南帮助产品经理使用AI编程规范体系快速生成产品需求文档（PRD）。

## 角色定位

作为产品经理，你是产品需求的定义者，负责：
- 定义产品功能和业务规则
- 编写产品需求文档（PRD）
- 与架构师、开发人员、测试人员协作

## 你将使用的技能

| 技能 | 用途 | 使用场景 |
|------|------|----------|
| prd-generator | 生成PRD文档 | 新功能需求、产品迭代、需求变更 |

## 快速开始

### 步骤1：准备需求输入

在使用AI生成PRD之前，准备以下信息：

**必需信息**：
- 产品/功能名称
- 目标用户
- 核心功能描述
- 业务场景

**可选信息**（有则更好）：
- 竞品分析
- 用户调研数据
- 业务流程草图
- 原型图或线框图

### 步骤2：触发PRD生成

**方式一：直接描述需求**

```
我需要一个用户订单管理系统，主要功能包括：
- 订单创建和编辑
- 订单审批流程
- 订单查询和统计
目标用户是电商平台的运营人员
```

**方式二：提供需求草稿**

```
请根据以下需求草稿生成完整的PRD文档：

【需求草稿】
功能名称：用户权限管理
目标用户：系统管理员
核心功能：
1. 用户管理（增删改查）
2. 角色管理（角色定义、权限分配）
3. 部门管理（组织架构）
```

**方式三：基于现有文档补充**

```
请基于以下功能列表，补充完整的PRD文档：
【功能列表】
- 登录/注册
- 个人中心
- 消息通知
```

### 步骤3：验证生成的PRD

PRD生成后，检查以下内容：

**结构完整性检查**：
- [ ] 第一章：产品概述是否清晰
- [ ] 第二章：用户角色和权限是否定义
- [ ] 第三章：功能需求是否详尽
- [ ] 第四章：业务流程和规则是否完整
- [ ] 第五章：交互和页面设计是否合理
- [ ] 第六章：非功能需求是否覆盖
- [ ] 第七章：验收标准是否明确
- [ ] 第八章：附录和变更记录是否填写

**内容质量检查**：
- [ ] 功能描述是否无歧义
- [ ] 业务规则是否完整
- [ ] 异常场景是否覆盖（每个功能至少3个）
- [ ] 验收标准是否可测试

### 步骤4：迭代优化

如果生成的PRD有不足，可以：

```
请补充【订单审批】功能的异常场景
请细化【用户权限矩阵】
请添加【数据导出】的业务规则
```

## PRD文档结构说明

生成的PRD文档包含八个章节：

### 第一章：产品概述
- 产品定义和愿景
- 目标用户和使用场景
- 产品范围和边界
- 核心价值主张

### 第二章：用户角色与权限体系
- 角色定义（角色编号、名称、描述）
- 权限矩阵（角色×功能的权限关系）
- 角色配置规则

### 第三章：功能需求说明
- 功能模块总览
- 功能点详细说明（用户故事、前置条件、业务逻辑、异常处理）
- 功能依赖关系

### 第四章：业务流程与规则
- 核心业务流程（含流程图）
- 状态流转（含状态转换图）
- 业务规则汇总（编号管理）

### 第五章：交互与页面设计
- 页面清单与流转（含流转图）
- 核心页面交互说明
- 通用交互规范

### 第六章：非功能需求
- 性能要求
- 安全要求
- 兼容性要求
- 可用性要求

### 第七章：验收标准
- 功能验收标准
- 业务规则验收标准
- 非功能验收标准

### 第八章：附录与变更记录
- 术语解释
- 参考文档
- 待决事项
- 变更记录

## 最佳实践

### 1. 需求描述要具体

❌ 不好的描述：
```
做一个用户管理功能
```

✅ 好的描述：
```
用户管理功能，支持：
1. 用户列表展示（分页、搜索、筛选）
2. 新增用户（姓名、邮箱、手机号、部门）
3. 编辑用户信息
4. 禁用/启用用户
5. 批量导入用户
目标用户是系统管理员
```

### 2. 说明角色和权限

如果产品涉及多角色协作，务必说明：

```
本系统涉及以下角色：
- 管理员：可管理所有用户和配置
- 部门经理：可查看和管理本部门数据
- 普通员工：只能查看和操作自己的数据
```

### 3. 提供业务规则

复杂的业务规则要提前说明：

```
订单审批规则：
1. 金额 < 1000元：直属上级审批
2. 金额 1000-10000元：部门经理审批
3. 金额 > 10000元：总经理审批
4. 加急订单：可跳过一级审批
```

### 4. 指明边界条件

说明哪些功能不包含，避免范围蔓延：

```
本次需求不包含：
- 移动端适配
- 与外部系统集成
- 历史数据迁移
```

## 常见问题

### Q1: 生成的PRD太长怎么办？

可以按模块拆分：
```
请只生成【用户管理模块】的PRD
请只生成【订单模块】的功能需求
```

### Q2: 如何处理需求变更？

使用变更记录：
```
请更新PRD，新增【批量导出】功能
变更原因：运营团队需要批量导出用户数据
```

### Q3: PRD中的图表无法显示怎么办？

PRD中的流程图使用Mermaid语法，支持Mermaid的工具都能渲染：
- GitHub
- GitLab
- VS Code（安装Mermaid插件）
- Typora
- Notion

### Q4: 如何与团队协作？

PRD生成后：
1. 保存到项目的 `docs/` 目录
2. 通过Git进行版本管理
3. 使用变更记录追踪需求演进
4. 在需求评审会上基于PRD进行讨论

## 与其他角色的协作

| 协作对象 | 交付物 | 协作方式 |
|----------|--------|----------|
| 架构师 | PRD文档 | 架构师根据PRD生成架构概要 |
| 开发人员 | PRD文档 | 开发人员根据PRD进行功能开发 |
| 测试人员 | PRD文档 | 测试人员根据PRD生成测试用例 |

## 附录：PRD模板变量

在描述需求时，可以使用以下变量格式：

| 变量 | 说明 | 示例 |
|------|------|------|
| {产品名称} | 产品的名称 | 用户管理系统 |
| {版本号} | PRD版本 | 1.0.0 |
| {目标用户} | 主要用户群体 | 系统管理员 |
| {核心功能} | 主要功能点 | 用户CRUD、权限管理 |
| {业务场景} | 使用场景 | 企业内部用户管理 |

---

**提示**：PRD是需求的"契约"，质量直接影响后续的设计和开发。花时间打磨PRD，能大幅减少后期的返工和沟通成本。
