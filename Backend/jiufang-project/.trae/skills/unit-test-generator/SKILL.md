# 单元测试生成 Skill

## 核心原则
1. **代码先行，理解后测**：生成测试前，必须先读取并理解被测代码的业务逻辑、输入输出、边界条件和异常分支。未理解代码逻辑前，禁止生成测试。
2. **隔离测试**：单元测试必须隔离被测单元，所有外部依赖（数据库、网络、文件系统、第三方服务、其他模块）必须使用 Mock/Stub/Fake 替代，禁止在单元测试中引入真实外部依赖。
3. **覆盖完整**：测试用例必须覆盖正常路径、异常路径、边界条件和等价类划分，目标行覆盖率不低于 80%，分支覆盖率不低于 70%。
4. **可读可维护**：测试代码应具备自描述性，测试方法命名清晰，Arrange-Act-Assert（AAA）结构明确，避免过度使用魔法数字和复杂嵌套。
5. **可自动化运行**：生成的测试必须能在主流测试框架（JUnit、pytest、Jest、Mocha 等）中一键运行，无需人工干预。
6. **生成与执行分离，二次确认**：单元测试代码生成完毕后，必须先询问用户是否需要执行测试。用户明确确认执行后，才能运行测试套件。严禁在生成阶段擅自执行测试。
7. **统一存放，规范目录**：所有单元测试相关文件（测试代码、Mock 定义、测试工具类、Fixture/Factory、测试配置文件）必须统一存放在项目约定的标准测试目录中，禁止分散存放或与源码混合。

## 执行工作流

### 阶段一：代码研读与分析（自动执行）
1. **读取被测代码**：读取用户指定的源文件或代码片段，若用户未指定，主动询问目标文件路径。
2. **提取测试维度**：
   - 公共接口（函数签名、输入参数、返回值类型）
   - 业务分支（if/else、switch、try-catch 等分支点）
   - 异常抛出（参数校验、业务规则校验抛出的异常类型和消息）
   - 外部依赖（数据库访问、HTTP 调用、文件读写、时间/随机数等）
   - 边界条件（空值、空字符串、极值、边界长度、特殊字符）
3. **识别测试框架**：本项目为Go项目，优先使用 **Go testing + testify + gomock** 组合。若项目已有测试文件，优先沿用现有框架和风格；若项目无现有测试，按以下优先级选择：
   - **首选**：Go标准库 `testing` + `github.com/stretchr/testify`（断言和Mock）+ `github.com/golang/mock`（接口Mock）
   - **备选**：Ginkgo（BDD风格）+ Gomega（断言）

4. **确定统一存放目录**：
   - **Go项目**：测试文件使用 `*_test.go` 命名，与源码同目录存放（Go语言强制惯例）
   - Java/Maven：`src/test/java/`（与 `src/main/java/` 镜像目录结构）
   - Java/Gradle：`src/test/java/`
   - Python：`tests/` 或 `src/tests/`
   - JavaScript/TypeScript：`__tests__/` 或 `tests/` 或 `src/**/*.spec.ts`
   - 若项目已有测试目录，优先沿用现有结构，确保新增测试文件与已有测试统一存放

### 阶段二：测试方案制定（必须输出）
基于阶段一分析，输出《单元测试实施方案》，格式如下：

```markdown
## 📋 单元测试实施方案

### 1. 被测对象
- 文件路径：
- 被测类/函数：
- 编程语言与测试框架：

### 2. 统一存放目录
- 测试根目录：
- 测试文件存放路径：（与被测代码镜像对应或统一 tests/ 目录）
- Mock/Fixture/工具类存放路径：

### 3. 测试维度与用例清单
| 用例编号 | 测试场景 | 输入 | 预期输出/行为 | 备注 |
|---------|---------|------|-------------|------|
| TC-01 | 正常流程 | ... | ... | |
| TC-02 | 异常输入-空值 | ... | 抛出 XXXError | |
| TC-03 | 边界条件-最大值 | ... | ... | |

### 4. Mock 策略
- 需 Mock 的外部依赖：
- Mock 工具：
- Mock 返回值设计：

### 5. 覆盖率目标
- 行覆盖率：≥ %
- 分支覆盖率：≥ %

### 6. 文件结构（统一存放）
```
project-root/
├── internal/                    # Go项目源码目录
│   ├── service/
│   │   ├── user_service.go      # 业务逻辑
│   │   └── user_service_test.go # 单元测试（与源码同目录）
│   ├── repository/
│   │   ├── user_repository.go
│   │   └── user_repository_test.go
│   └── mocks/                   # Mock文件统一存放
│       ├── mock_user_repository.go
│       └── mock_email_service.go
├── pkg/
│   └── utils/
│       ├── helper.go
│       └── helper_test.go
├── go.mod
└── go.sum
```

**Go项目测试文件命名规范**：
- 测试文件：`<原文件名>_test.go`，与源码文件同目录
- Mock文件：`mock_<接口名>.go`，统一存放在 `internal/mocks/` 或对应模块的 `mocks/` 目录
- 测试工具类：存放在 `internal/testutil/` 或 `pkg/testutil/` 目录

### 7. 规范合规自检项
- [ ] 测试命名符合规范（Given_When_Then 或 test_xxx_xxx）
- [ ] 遵循 AAA 结构
- [ ] 所有外部依赖已 Mock
- [ ] 边界条件和异常分支已覆盖
- [ ] 测试文件统一存放在标准测试目录，未与源码混合
```

**输出后，AI 必须明确提示：**
> 以上是针对「XXX模块/函数」的单元测试实施方案。请审阅方案内容，确认无误后回复「确认执行」，我将严格按照本方案生成测试代码。若需调整，请直接指出修改点。

### 阶段三：等待用户确认（第一阻断点）
- **若用户未明确确认**：仅回答疑问、接受修改意见、更新方案，**绝不**生成测试代码或创建测试文件。
- **若用户明确确认**（如回复"确认"、"同意"、"执行"、"按方案来"）：进入阶段四。
- **此阻断机制适用于所有场景（生成单元测试、补充测试用例、修改现有单元测试），无任何例外。**

### 阶段四：测试代码生成（确认后执行）
1. **统一目录创建**：
   - 严格按照方案中的「统一存放目录」创建测试文件，禁止将测试文件写入源码目录（`src/main/`）
   - 测试文件路径应与被测代码保持镜像结构（如 `src/main/java/com/example/UserService.java` 对应 `src/test/java/com/example/UserServiceTest.java`）
   - Mock、Fixture、工具类统一存放在测试根目录下的 `mocks/`、`fixtures/`、`utils/` 子目录中

2. **逐函数/逐类生成**：按方案中的用例清单顺序生成测试代码，每完成一个被测单元简要汇报进度。

3. **文件注释头**：每个测试文件顶部添加注释头（作者、日期、被测对象、功能描述）。

4. **Mock 实现**：为所有外部依赖编写 Mock/Stub，统一存放在测试目录的 `mocks/` 或 `__mocks__/` 中，确保测试可独立运行。

5. **断言精确**：断言必须精确验证返回值、异常类型、异常消息、Mock 调用次数和参数，避免宽泛断言（如 `assertTrue(True)`）。

6. **参数化测试**：对于多组等价类输入，优先使用参数化测试（pytest.mark.parametrize、JUnit @ParameterizedTest 等）减少代码冗余。

7. **实时自检**：
   - 每生成一个测试用例，对照方案检查是否遗漏分支或边界条件
   - 检查测试文件是否存放在正确的统一目录中，未与源码混合

8. **阶段四完成汇报**：
   - 输出《测试代码交付清单》，列出所有新建/修改的测试文件及其统一存放路径
   - 明确提示用户：
     > 单元测试代码已全部生成完毕，所有测试相关文件已统一存放在「XXX目录」下。请问是否需要现在执行测试套件？
     > 如需执行，请回复「执行测试」或「确认运行」，我将启动测试框架并运行所有单元测试。
     > 如暂不需要执行，可回复「不执行」或忽略此消息。

### 阶段五：等待用户确认是否执行（第二阻断点，绝对不可绕过）
- **若用户未明确要求执行或回复「不执行」**：不执行任何测试命令，仅回答疑问或接受进一步修改意见。
- **若用户明确要求执行**（如回复"执行测试"、"确认运行"、"运行"、"执行"）：进入阶段六。
- **此阻断机制适用于所有场景，无任何例外。严禁在阶段四完成后自动执行测试。**

### 阶段六：测试执行与交付（用户确认执行后）
1. **执行测试**：
   - 根据项目测试框架的执行命令（如 `mvn test`、`pytest tests/`、`jest`、`go test ./...`），运行单元测试套件
   - 捕获并展示测试结果（通过数、失败数、错误日志、覆盖率报告）
   - 若测试失败，分析失败原因，输出诊断报告，不擅自修改被测业务代码来"让测试通过"

2. **输出《单元测试执行报告》**：
   - 执行命令
   - 通过率（通过数 / 总数）
   - 覆盖率数据（行覆盖率、分支覆盖率，如有）
   - 失败用例及原因分析（如有）

3. **输出《规范符合性声明》**：
   - 声明已遵循代码规范文档的关键条款
   - 声明所有测试文件已统一存放，未与源码混合

4. **询问用户**：
   - 是否需要补充集成测试、性能测试或测试数据构造
   - 是否需要根据测试结果调整测试用例或修复被测代码

## 测试策略规范

### 1. 命名规范
- 测试类：`TestXxx` 或 `XxxTest`
- 测试方法：
  - Python：`test_xxx_xxx` 或 `test_given_when_then`
  - Java：`shouldXxxWhenXxx` 或 `testXxxXxx`
  - JS/TS：`should xxx when xxx` 或 `test xxx xxx`
  - Go：`TestXxx` / `Test_Xxx_xxx`

### 2. 结构规范（AAA）
```go
func TestRegister_ValidInput_ShouldSucceed(t *testing.T) {
    // Arrange
    ctrl := gomock.NewController(t)
    defer ctrl.Finish()
    
    mockRepo := NewMockUserRepository(ctrl)
    mockRepo.EXPECT().FindByEmail("a@b.com").Return(nil, nil)
    mockRepo.EXPECT().Save(gomock.Any()).Return(nil)
    
    service := NewUserService(mockRepo)

    // Act
    result, err := service.Register("a@b.com", "Alice", "123456")

    // Assert
    assert.NoError(t, err)
    assert.Equal(t, "a@b.com", result.Email)
}
```

### 3. 覆盖维度（必须覆盖）
| 维度     | 说明        | 示例                    |
| ------ | --------- | --------------------- |
| 正常路径   | 标准输入，预期成功 | 合法参数调用，验证返回值          |
| 异常输入   | 非法/畸形参数   | null、空字符串、类型错误、格式错误   |
| 边界条件   | 临界值       | 最小长度、最大长度、空集合、极值      |
| 业务规则异常 | 业务约束不满足   | 重复注册、余额不足、权限不足        |
| 外部依赖异常 | 依赖返回错误/超时 | Mock 抛异常、返回空、返回错误码    |
| 状态变更   | 副作用验证     | 数据库是否写入、邮件是否发送、日志是否记录 |

### 4. Mock 规范
- 只 Mock 被测单元**直接依赖**的外部对象，不 Mock 被测单元内部逻辑。
- Mock 后必须验证**调用次数**和**传入参数**，确保交互正确。
- Mock 类/模块统一存放在测试目录的 `mocks/` 或 `__mocks__/` 子目录中。
- 禁止在单元测试中访问真实数据库、网络、文件系统。
- **Go 生态 Mock 工具推荐**：
  - **gomock**：官方推荐，接口 Mock 首选，配合 mockgen 生成
  - **testify/mock**： testify 套件自带，API 友好
  - **go-sqlmock**：数据库驱动 Mock，用于 SQL 测试
  - **httptest**：HTTP 服务 Mock，标准库自带
  - **miniredis**：Redis Mock，用于缓存测试

### 5. 统一存放规范
| 语言/框架 | 源码目录 | 测试统一存放目录 | 备注 |
|-----------|---------|----------------|------|
| Java/Maven | `src/main/java/` | `src/test/java/` | 镜像包结构 |
| Java/Gradle | `src/main/java/` | `src/test/java/` | 镜像包结构 |
| Python | `src/` 或根目录 | `tests/` | pytest 惯例 |
| JavaScript | `src/` | `__tests__/` 或 `tests/` | Jest 惯例 |
| TypeScript | `src/` | `src/**/*.spec.ts` 或 `tests/` | 按项目约定 |
| Go | 与源码同包 | `*_test.go` 同目录 | Go 语言强制惯例 |
- **禁止**将测试文件、Mock、Fixture 写入 `src/main/` 或生产源码目录。
- **禁止**测试文件散落在多个非标准目录中。

## 禁止事项
- ❌ 禁止未理解被测代码逻辑就直接生成测试。
- ❌ 禁止生成无法独立运行的测试（依赖真实数据库/网络/文件）。
- ❌ 禁止在方案未经用户确认（第一阻断点）前生成测试代码。
- ❌ 禁止在测试代码生成完毕后未经用户确认（第二阻断点）前擅自执行测试。
- ❌ 禁止将测试文件、Mock、Fixture 写入生产源码目录（如 `src/main/`）。
- ❌ 禁止测试文件分散存放，必须统一存放在项目标准测试目录中。
- ❌ 禁止使用过于宽泛的断言（如 `assertTrue(True)`、`assertIsNotNone` 无后续验证）。
- ❌ 禁止遗漏异常分支和边界条件的测试覆盖。
- ❌ 禁止修改被测源代码以适配测试（除非用户明确要求重构）。
- ❌ 禁止生成与被测代码语言/框架不匹配的测试代码。

## 引用资源
- 优先沿用项目已有的测试框架、Mock 工具和命名风格。
- 若项目无现有测试，按语言生态默认推荐选择框架。
- 优先沿用项目已有的测试目录结构，确保新增测试与已有测试统一存放。
