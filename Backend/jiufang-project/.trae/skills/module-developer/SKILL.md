# 功能开发与修改 Skill

## 核心原则
1. **文档先行，绝不绕过**：任何功能开发（包括新功能开发、原有功能修改、功能追加）开始前，必须先检查并读取相关项目文档。这一步为强制步骤，**绝对不允许跳过或绕过**，即使文档路径不存在，也必须询问用户并明确处理。
2. **方案先行，确认执行**：任何代码生成前，必须先输出完整实施方案，等待用户明确确认（如回复"确认"、"同意"、"执行"、"按方案来"）。**无论开发新功能、修改原有功能还是追加功能，均严格执行此原则，绝不例外。**
3. **阻断执行，未经确认不动手**：在用户明确确认方案之前，**严禁生成任何可运行代码、创建任何文件、修改任何现有代码**。此阻断机制适用于所有场景，无例外。
4. **文档驱动**：严格基于项目已有的 PRD、技术架构概要、详细技术设计文档和代码规范文档进行分析和实现。
5. **规范合规**：所有生成的代码、文件命名、目录结构、接口定义必须符合项目代码规范文档。
6. **增量交付**：方案确认后，按模块/分层逐步生成代码，每完成一个关键步骤主动汇报。

## 执行工作流

### 阶段一：文档研读与需求分析（自动执行，强制步骤）
当本技能被触发后，AI 必须首先执行以下步骤，**不得跳过、不得绕过**：

1. **读取项目文档**（使用文件工具读取，必须全部读取完成后才能进入下一步）：
   - **PRD 文档**：`docs/PRD.md` 或 `docs/prd.md` 或用户指定的 PRD 文档路径
   - **架构文档**：`docs/architecture.md` 或 `docs/技术架构概要.md` 或相关架构文档
   - **设计文档**：`docs/detailed-design.md` 或 `docs/详细技术设计.md` 或相关设计文档
   - **Trae规则文件**：`.trae/rules/go-base.md`、`.trae/rules/gin-base.md`、`.trae/rules/gin-project.md`（或 `gin-eino-project.md`）

   **文档读取规则**：
   - AI 必须依次尝试读取以上四类文档
   - 必须全部读取完成后，才能执行后续的分析步骤
   - **若有用户指定的文档路径**，优先使用用户指定的路径，不使用默认路径
   - **只要有任何一个文档未读取到**（路径不存在或无法读取），AI 必须立即询问用户
   - 用户确认可以跳过该文档后，才能跳过；否则必须继续尝试读取或终止执行
   - **此规则适用于所有场景（新功能开发、原有功能修改、功能追加），无例外**

2. **分析并提取关键信息**：
   - 功能/模块的业务边界与核心功能点（来自 PRD）
   - 技术选型与架构位置（来自架构概要）
   - 数据模型、接口契约、状态机、异常策略（来自详细设计）
   - 命名规范、目录规范、代码风格、注释要求（来自代码规范）
   - **若为修改/追加场景**：额外分析现有代码影响范围、依赖关系、回滚风险

3. **一致性检查**：
   - 检查 PRD 需求是否在详细设计中有对应实现方案
   - 检查详细设计是否符合架构概要的分层/分域原则
   - **若为修改/追加场景**：检查变更是否与现有架构冲突，是否破坏已有接口契约
   - 若发现文档冲突或缺失，在方案中标注风险点，不擅自假设

### 阶段二：方案制定（必须输出）
基于阶段一的分析，输出《功能开发/修改实施方案》，格式如下：

```markdown
## 📋 功能开发/修改实施方案

### 1. 功能概述
- 功能/模块名称：
- 所属领域/分层：
- 业务目标：
- **变更类型**：□ 新功能开发  □ 原有功能修改  □ 功能追加

### 2. 目录与文件结构
（严格遵循代码规范文档，列出将创建或修改的所有目录和关键文件）

```
project-root/
├── ...
```

### 3. 核心数据模型 / API 接口 / 页面路由
（列出新增或变更的核心定义，若涉及数据库需包含字段、索引、关联关系；若为修改场景，需标注变更前后对比）

### 4. 影响范围分析（修改/追加场景必填）
- 受影响的现有模块/接口/页面：
- 依赖关系变更：
- 数据迁移/兼容性处理：

### 5. 实现步骤（分阶段）
- Step 1：基础设施/数据层
  - 数据模型定义（Model/Entity）
  - **数据库迁移脚本**：如涉及表结构变更（新增表、新增字段、修改字段类型、创建索引、删除字段等），**必须先使用 `database-migrator` skill** 生成专业的迁移脚本和回滚脚本，确保数据库变更可追溯、可回滚
- Step 2：领域服务/业务逻辑层
- Step 3：接口适配/控制器/页面层
- Step 4：单元测试/集成测试/回归测试

### 6. 关键设计决策与风险点
- 决策1：（说明原因）
- 风险1：（说明缓解措施）

### 7. 规范合规自检项
- [ ] 文件命名符合规范
- [ ] 代码风格符合规范
- [ ] 接口命名与版本策略符合规范
- [ ] 错误码/异常处理符合规范
- [ ] 修改场景已评估对现有功能的影响
```

**输出后，AI 必须明确提示：**
> 以上是针对「XXX功能/模块」的开发/修改实施方案。请审阅方案内容，确认无误后回复「确认执行」，我将严格按照本方案开始生成代码。若需调整，请直接指出修改点。

### 阶段三：等待用户确认（阻断点，绝对不可绕过）
- **若用户未明确确认**：仅回答疑问、接受修改意见、更新方案，**绝不**创建任何文件、生成实现代码或修改现有代码。
- **若用户明确确认**（如回复"确认"、"同意"、"执行"、"按方案来"）：进入阶段四。
- **此阻断机制适用于所有场景（新功能开发、原有功能修改、功能追加），无任何例外情况。**

### 阶段四：代码生成与实施（确认后执行）
1. **按方案中的步骤顺序**逐层生成代码，每完成一个 Step 简要汇报进度。
2. **每生成或修改一个文件**，必须在文件顶部或合适位置添加基于代码规范要求的注释头（如作者、日期、功能描述、变更说明）。
3. **实时自检**：每生成或修改一段核心逻辑，对照详细设计文档检查是否遗漏需求。
4. **代码规范校验**：确保命名、缩进、异常处理、日志打印等符合代码规范文档。
5. **修改场景特殊要求**：修改现有代码时，必须确保不破坏原有功能，必要时提供回滚说明。

### 阶段五：交付与复盘（生成完成后）
1. 输出《功能交付清单》，列出所有新建/修改的文件。
2. 输出《规范符合性声明》，声明已遵循代码规范文档的关键条款。
3. **若为修改/追加场景**：输出《回归测试建议》，列出需要验证的现有功能点。
4. 询问用户是否需要补充单元测试、接口文档或部署配置。

## 禁止事项
- ❌ **禁止在阶段一完成前跳过文档读取，进入任何后续阶段。**
- ❌ **禁止在阶段二完成前生成任何可运行代码或创建文件。**
- ❌ **禁止在阶段三用户未确认前执行阶段四，无论任何理由。**
- ❌ **禁止擅自修改已有模块的代码，除非方案中明确列出且用户确认。**
- ❌ **禁止使用项目规范中未列出的技术栈或命名风格。**
- ❌ **禁止忽略文档中的异常处理、安全、性能等非功能性要求。**
- ❌ **禁止在修改场景下未做影响评估直接改动现有代码。**

## 引用资源
- 本技能执行时，应将项目内的 PRD、架构概要、详细设计、代码规范文档作为首要上下文参考。
- **Trae 规则文件**：优先读取 `.trae/rules/` 目录下的项目规则文件（如 `go-base.md`、`gin-base.md`、`gin-project.md`、`gin-eino-project.md`），这些规则文件定义了项目的技术栈规范、代码风格和最佳实践。
- **日志与监控规范**：`.trae/rules/gin-base.md` 中定义了日志框架选择（zap）、日志级别使用规范、日志埋点规范、Prometheus监控集成等，功能开发时应遵循这些规范。
- **关联Skill**：
  - `database-migrator`：功能开发涉及数据库表结构变更时，应使用此skill生成迁移脚本
  - `unit-test-generator`：功能开发完成后，应使用此skill生成单元测试
  - `api-doc-generator`：功能开发完成后，应使用此skill生成API文档
- 若项目文档路径与上述默认路径不一致，优先以用户当前对话中指定的路径为准。
